# WebPass v1.2.0 自助修改登录密码设计规格

## 目标

允许所有已认证且账号仍处于启用状态的用户，在独立页面修改自己的登录密码。复用现有 `AppUser` 字段、`IPasswordHasher`、审计基础设施、Cookie 会话、二次验证授权和并发机制，不引入另一套密码体系或授权撤销机制。

## 范围

本次只增加自助修改密码工作流、账户区入口、审计展示、必要样式、文档和测试。管理员重置密码、登录、Cookie 生命周期、账号锁定、权限授权、密码二次验证、Secret Reveal 以及其他业务功能继续沿用现有架构。

不修改 EF Core 实体、数据库映射、模型快照、migration 或历史数据。

## 当前行为与根因

`AppUser` 已经包含 `PasswordHash`、`IsEnabled`、`FailedLoginCount`、`LockedUntil`、`MustChangePassword` 和 `RowVersion`。登录、管理员重置和敏感操作二次验证也已使用现有 `IPasswordHasher`，但系统没有处理当前用户自助改密的服务或 Razor Page。账户区域只有退出入口，`README.md` 还明确把自助改密列为当前范围之外。

因此根因是工作流尚未实现，而不是 schema 或密码哈希缺陷。

## 选定架构

### 独立密码修改服务

在 `Infrastructure/Identity` 下新增 `PasswordChangeService`。该服务负责安全敏感的状态变更，接收当前认证用户 ID、当前密码、新密码和取消令牌。

每次修改必须：

1. 按当前认证用户 ID 查询并跟踪 `AppUser`；
2. 用户不存在或已停用时拒绝；
3. 新密码为空或全空白时拒绝，与现有管理员初始化密码规则保持一致；
4. 只使用 `IPasswordHasher.Verify` 验证当前密码；
5. 只使用 `IPasswordHasher.Hash` 生成新哈希；
6. 更新 `PasswordHash` 并清除 `MustChangePassword`；
7. 保留 `FailedLoginCount`、`LockedUntil`、角色、权限和启用状态；
8. 依靠被跟踪的 `RowVersion` 检测乐观并发；
9. 在同一个关系型数据库事务中提交密码更新和成功审计。

服务为成功、用户不可用、当前密码错误、新密码无效和并发冲突返回明确且不敏感的结果。服务不得返回或记录提交的密码或密码哈希。

### 独立 Razor Page

新增需要认证的 `/account/change-password` Razor Page。GET 和 POST 都从 `ClaimTypes.NameIdentifier` 获取用户 ID，声明缺失或格式错误时拒绝。GET 检查对应用户仍然存在并处于启用状态；POST 通过 `PasswordChangeService` 重新检查，因此用户加载表单后如果被停用，也无法完成修改。

表单包含：

- 当前密码，使用 `autocomplete="current-password"`；
- 新密码，使用 `autocomplete="new-password"`；
- 确认新密码，使用 `autocomplete="new-password"`。

三个字段均为必填，确认密码必须与新密码完全一致。现有密码规则只有“不得为空或全空白”；本次不增加长度、复杂度、密码历史或“不得与当前密码相同”等规则。

页面为 POST 请求复用现有的逐用户密码二次验证限流策略，不定义新的限流体系。验证和服务错误使用固定中文提示。无效表单重新渲染前，PageModel 必须清除所有密码值和 ModelState 中的尝试值，同时保留安全的验证消息，防止响应回显提交的凭据。

成功后设置不敏感的状态消息，并通过 POST/Redirect/GET 重定向回本页。现有登录 Cookie 保持有效。

### 账户区入口

在 `_Layout.cshtml` 的已认证账户区域增加“修改密码”链接，与现有退出控件并列。退出继续使用 POST 表单。只增加保证两个操作在桌面、折叠侧栏、平板和手机布局中可用所必需的 CSS。

## 审计设计

复用现有 `AuditLogs` 表和 `AuditWriter`：

- `Action`：`UserPasswordChange`
- `ObjectType`：`User`
- `ObjectId`：当前认证用户 ID
- `ActorUserId`：同一个当前认证用户 ID
- `Result`：`Success`
- payload/details：无

增加稳定中文审计标签“修改自己的登录密码”。操作人与对象是同一个用户，因此能够表达自助操作，同时遵循现有 `UserPasswordReset` 命名规范。当前密码、新密码、确认密码、旧哈希和新哈希都不得进入审计数据、状态消息、响应 HTML 或异常文本。

只有成功修改必须写入该动作。被拒绝的尝试使用固定页面错误和现有限流，不修改登录失败计数，也不增加额外审计类别。

## 会话与二次验证行为

修改密码后不退出当前会话，也不撤销其他已经签发的登录 Cookie。Cookie 空闲期限和绝对期限继续为 30 分钟和 8 小时。这符合“不新增撤销表或重复失效机制”的明确限制。

在 SQL Server 中，更新用户会改变 `RowVersion`。现有五分钟 Secret Reveal 二次验证授权已经绑定该行版本，因此之前签发的授权会自然失效，无需新增撤销代码或数据表。

对于已经认证的用户，`LockedUntil` 不作为额外改密门槛；当前密码验证失败也不增加 `FailedLoginCount`。这与现有二次验证行为一致，并避免改变登录锁定架构。`IsEnabled` 是本功能要求的明确账号状态门槛。

## 数据模型、Migration 与历史回填

现有实体和数据库已经包含工作流所需的全部字段。不得修改 `AppUser`、`WebPassDbContext`、`WebPassDbContextModelSnapshot` 或任何 migration 文件，不创建 migration。

不回填历史数据。现有密码哈希保持不变，直到用户成功修改自己的密码；现有 `MustChangePassword` 值保持不变，直到成功自助改密时清除。现有锁定状态、权限、角色、审计和会话都保持不变。

发布继续遵循 `DEPLOYMENT.md`，并重新构建与提交匹配的 migration bundle。由于没有新 migration，本功能不会通过 bundle 执行 schema 或数据迁移。

## 错误与并发处理

- 用户不存在、用户已停用或身份声明无效时拒绝，且不修改密码状态。
- 当前密码错误时返回统一提示，不暴露验证细节。
- 新密码为空或全空白、确认密码不一致时返回安全验证错误。
- `DbUpdateConcurrencyException` 返回重试提示且不写成功审计；并发发生的密码重置、停用或其他用户行修改不得被覆盖。
- 在关系型数据库中，密码更新与成功审计原子提交；审计持久化失败时回滚密码更新。

## 测试

- 服务单元测试覆盖：成功修改、修改后旧密码失效、新密码可验证、清除 `MustChangePassword`、保留锁定和账号结构、拒绝已停用或不存在的用户、拒绝错误当前密码，以及成功审计不含敏感信息。
- 页面集成测试覆盖：认证、GET 和 POST 的启用状态检查、带防伪令牌的成功提交、确认密码不一致、当前密码错误、固定安全提示、复用限流，以及响应和审计中不出现提交密码或哈希。
- 扩展现有展示测试，验证响应式账户区域同时保留“修改密码”和 POST 退出。
- 审计标签测试覆盖 `UserPasswordChange`。
- 先运行新增及受影响的聚焦测试，再执行一次完整解决方案测试，并确认 migration 和模型快照没有差异。

## 未采用方案

- 直接在 PageModel 中实现虽然文件更少，但会把凭据验证、持久化、并发、事务和审计与 HTTP 展示耦合。
- 复用 `ReauthenticationService` 会错误地把改密与五分钟 Secret Reveal 授权绑定，并改变现有敏感密码架构。
- 增加密码修改时间、会话世代、撤销表或其他授权失效字段会引入 schema 与会话重构，超出本功能范围。

## 风险

- 现有密码规则接受任何非空白字符串，也允许复用当前密码。本设计有意保持该规则，不引入未经要求的新策略。
- 修改密码后，现有登录 Cookie（包括其他浏览器中的 Cookie）会继续有效，直到正常过期。需要立即终止访问时，管理员仍应停用账号。
- 登录当前并不强制执行 `MustChangePassword`，管理员创建和重置也会将其写为 `false`。本功能只在成功自助改密后清除该字段，不引入首次登录强制跳转。
- 账号停用后，过期前的认证 Cookie 仍可能渲染通用应用外壳，因为 principal 校验不会查询数据库。修改密码页在 GET 和 POST 中独立拒绝该用户，不借此重构全局 Cookie 校验。
