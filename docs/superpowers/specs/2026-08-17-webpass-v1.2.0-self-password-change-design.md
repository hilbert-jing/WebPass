# WebPass v1.2.0 Self-Service Password Change Design

## Goal

Allow every authenticated user whose account is still enabled to change their own login password from a dedicated page. Reuse the existing `AppUser` fields, `IPasswordHasher`, audit infrastructure, cookie session, reauthentication grant, and concurrency behavior without introducing another password scheme or authorization-revocation mechanism.

## Scope

The change is limited to a self-service password-change workflow, its account-area entry, audit presentation, focused styling, documentation, and tests. Administrator password reset, login, cookie lifetime, account lockout, permission authorization, secret reauthentication, secret reveal, and all unrelated business functions keep their existing architecture.

No EF Core entity, database mapping, model snapshot, migration, or historical-data update is required.

## Current Behavior and Root Cause

`AppUser` already stores `PasswordHash`, `IsEnabled`, `FailedLoginCount`, `LockedUntil`, `MustChangePassword`, and `RowVersion`. Login, administrator reset, and secret reauthentication already use the existing `IPasswordHasher`, but there is no service or Razor Page for changing the authenticated user's own password. The account area exposes only logout, and `README.md` explicitly lists self-service password change as out of scope.

The missing behavior is therefore an unimplemented workflow rather than a schema or hashing defect.

## Chosen Architecture

### Dedicated Password Change Service

Add `PasswordChangeService` under `Infrastructure/Identity`. It owns the security-sensitive state transition and accepts the authenticated user ID, current password, new password, and cancellation token.

For each change attempt the service must:

1. query the tracked `AppUser` by the supplied authenticated user ID;
2. reject a missing or disabled user;
3. reject an empty or whitespace-only new password, matching the existing administrator-initialization password rule;
4. verify the current password only through `IPasswordHasher.Verify`;
5. create the replacement hash only through `IPasswordHasher.Hash`;
6. update `PasswordHash` and clear `MustChangePassword`;
7. preserve `FailedLoginCount`, `LockedUntil`, role, permissions, and enablement;
8. rely on the tracked `RowVersion` for optimistic-concurrency detection;
9. write the password update and success audit inside the same relational transaction.

The service returns explicit non-sensitive outcomes for success, unavailable user, incorrect current password, invalid new password, and concurrency conflict. It must never return or log a submitted password or password hash.

### Dedicated Razor Page

Add `/account/change-password` as an authenticated Razor Page. Both GET and POST obtain the user ID from `ClaimTypes.NameIdentifier` and reject an absent or invalid identifier. GET checks that the corresponding user still exists and is enabled. POST performs the same check through `PasswordChangeService`, so a user disabled after loading the form cannot complete the change.

The form contains:

- current password with `autocomplete="current-password"`;
- new password with `autocomplete="new-password"`;
- new-password confirmation with `autocomplete="new-password"`.

All fields are required, and confirmation must exactly match the new password. The existing password rule is only non-empty/non-whitespace; this change does not add length, complexity, history, or different-from-current requirements.

The page reuses the existing per-user secret-reauthentication rate-limit policy for POST requests instead of defining a new rate-limiting system. Validation and service errors use fixed Chinese messages. Before re-rendering an invalid form, the PageModel clears all password values and their ModelState attempted values while preserving safe validation messages, so the response cannot echo submitted credentials.

On success the page sets a non-sensitive status message and redirects to itself using the POST/Redirect/GET pattern. The existing login cookie remains valid.

### Account-Area Entry

Add a `修改密码` link to the authenticated account area in `_Layout.cshtml`, next to the existing logout control. Logout remains a POST form. Add only the CSS necessary for the two controls to remain usable in desktop, collapsed-sidebar, tablet, and mobile layouts.

## Audit Design

Reuse the existing `AuditLogs` table and `AuditWriter`:

- `Action`: `UserPasswordChange`
- `ObjectType`: `User`
- `ObjectId`: the authenticated user's ID
- `ActorUserId`: the same authenticated user's ID
- `Result`: `Success`
- payload/details: none

Add the stable Chinese audit label `修改自己的登录密码`. The actor and object being the same user makes the action self-service while following the existing `UserPasswordReset` naming convention. Current password, new password, confirmation, old hash, and new hash must not enter audit data, status messages, response HTML, or exception text.

Only a successful change is required to create this action. Rejected attempts reuse fixed UI errors and the existing rate limit; they do not change login failure counters or create additional audit categories.

## Session and Reauthentication Behavior

Password change does not sign out the current session and does not revoke other issued login cookies. Cookie idle and absolute lifetimes remain 30 minutes and eight hours. This matches the explicit constraint not to add a revocation table or duplicate invalidation mechanism.

On SQL Server, updating the user changes `RowVersion`. Existing five-minute secret reauthentication grants are already bound to that row version, so a previously issued grant naturally becomes invalid without any new revocation code or table.

`LockedUntil` is not an additional password-change gate for an already authenticated user, and a failed current-password check does not increment `FailedLoginCount`. This follows the existing reauthentication behavior and avoids changing the login lockout architecture. `IsEnabled` remains the explicit account-state gate required by this feature.

## Data Model, Migration, and Backfill

The existing entity and database already contain every field needed by the workflow. Do not edit `AppUser`, `WebPassDbContext`, `WebPassDbContextModelSnapshot`, or any migration file. Do not create a migration.

No historical data is backfilled. Existing password hashes remain untouched until their owners successfully change them. Existing `MustChangePassword` values remain unchanged until a successful self-service change clears the flag. Existing lockout state, permissions, roles, audits, and sessions remain unchanged.

The release continues to follow `DEPLOYMENT.md` and must rebuild the commit-matched migration bundle. Because there is no new migration, the bundle performs no schema or data transition for this feature.

## Error and Concurrency Handling

- Missing user, disabled user, or invalid identity claim is rejected without changing password state.
- Incorrect current password returns a generic current-password error without exposing verification details.
- Empty/whitespace new password and confirmation mismatch are handled as safe validation errors.
- `DbUpdateConcurrencyException` produces a retry message and no success audit; a concurrent reset, disable, or other user-row change must win rather than being overwritten.
- On relational providers, the password update and success audit commit atomically. If audit persistence fails, the password update is rolled back.

## Testing

- Service unit tests cover success, old-password rejection after change, new-password verification, clearing `MustChangePassword`, preservation of lockout and account shape, disabled/missing user rejection, incorrect-current-password rejection, and a redacted success audit.
- Page integration tests cover authentication, enabled-state checks on GET and POST, antiforgery-protected success, confirmation mismatch, incorrect current password, fixed safe errors, rate-limit reuse, and absence of submitted passwords or hashes from rendered responses and audit data.
- Existing presentation tests are extended to verify that `修改密码` and POST logout remain together in the account area across responsive layout contracts.
- Audit-label tests cover `UserPasswordChange`.
- Run the focused new and affected tests first, then one complete solution test pass. Confirm that no migration or model-snapshot diff exists.

## Documentation

Update `README.md` to list self-service login-password change, remove it from the out-of-scope list, and document that password changes do not revoke issued login cookies. Update the production verification checklist in `DEPLOYMENT.md` to include an enabled user changing their password, the old password failing a subsequent login, the new password succeeding, and a redacted success audit.

## Alternatives Rejected

- Implementing the workflow directly in the PageModel would reduce the file count but mix credential verification, persistence, concurrency, transactions, and auditing with HTTP presentation.
- Reusing `ReauthenticationService` would incorrectly couple password change to the five-minute Secret Reveal grant and alter the existing sensitive-secret architecture.
- Adding a password-change timestamp, session epoch, revocation table, or separate authorization-invalidating field would require schema and session redesign outside this feature's scope.

## Risks

- The existing password rule accepts any non-whitespace string and does not prevent reusing the current password. This design deliberately preserves that rule instead of introducing an unrequested policy change.
- Existing login cookies remain valid after password change, including cookies in other browsers, until their normal expiry. Administrators must still disable an account when immediate access termination is required.
- `MustChangePassword` is not currently enforced by login, and administrator create/reset currently writes it as false. This feature only clears it after a successful self-service change; it does not introduce forced first-login redirection.
- A stale authenticated cookie may still render the general application shell after the account is disabled because principal validation does not query the database. The password-change page independently rejects that user on both GET and POST without redesigning global cookie validation.
