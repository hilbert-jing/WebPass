# WebPass v1.1.0 Usability Corrections Design

## Goal

Improve the server inventory without changing the password security flow or database schema: promote the password reveal action beside Edit and Ping, let users choose a page size from 1 through 500 safely, and let administrators Ping unregistered addresses from the full address pool without creating or mutating server assets.

## Scope

The change is limited to the server inventory page, the application Ping workflow, audit presentation labels, focused styling, and tests. Password reveal backend behavior, permissions, reauthentication, CSRF protection, automatic secret hiding, subnet management, asset registration, existing server Ping history, and deployment procedures remain unchanged.

No EF Core entity, database mapping, model snapshot, or migration changes are allowed.

## Current Behavior and Root Causes

### Password Reveal Placement

The reveal button and its output panel currently live inside the `details` element labeled `更多操作`. The JavaScript and backend security flow do not require that nesting, so this is a Razor structure issue only.

### Page Size

`Query.Take` and `Query.Skip` are hidden fields in the filter form. The page passes the bound `ServerListQuery` directly to `ServerAssetService.ListAsync`, whose defensive contract throws when `Take` is outside `1..500`. A handcrafted URL can therefore reach the service with an invalid value, and a filter submission preserves the old offset instead of returning to the first page.

### Unregistered Address Ping

Full-pool free rows are generated at query time and have no `ServerAssetId`. The current Ping service accepts only a server asset ID, validates a registered asset, always creates a `PingResult` with a required `ServerAssetId`, and scopes page feedback by asset ID. This design cannot probe a free address without incorrectly creating an asset or contaminating registered-server Ping history.

## Chosen Design

### Server Row Actions

Render registered-server controls in a focused `table-actions` container in this order when permitted:

1. `编辑`
2. `Ping`
3. `查看密码`
4. `更多操作`

Move the existing reveal button and panel out of the more-actions menu without changing their IDs, data attributes, antiforgery token source, script, endpoint, or timeout behavior. Render `更多操作` only when archive permission exists, and keep only the existing archive confirmation inside it. Add minimal flex styling so the primary actions are visually adjacent while feedback and secret panels remain separate blocks.

### Page-Size Normalization

Replace the hidden `Query.Take` filter field with a labeled numeric input using `min="1"` and `max="500"`. Submit `Query.Skip=0` from the filter form so applying filters or changing page size always starts at the beginning. Previous and next forms continue carrying the normalized `Query.Take`.

Normalize the page-bound query before calling `ServerAssetService.ListAsync`:

- clamp `Take` to `1..500`;
- clamp negative `Skip` to `0` as the matching safe boundary;
- preserve model-binding errors for malformed non-numeric inputs.

Keep `ServerAssetService.ValidateQuery` unchanged so non-UI callers retain the strict defensive contract.

### Shared Ping Probe Core

Add an application-only `PingProbeResult` carrying the canonical target IP, normalized outcome, latency, and safe error code. Refactor `PingService` so registered and unregistered operations share one private transport execution path responsible for:

- the configured timeout;
- the existing process-wide concurrency gate;
- the existing per-user one-minute allowance;
- `IPingTransport` invocation;
- exception conversion;
- outcome and error-code normalization.

The registered `ExecuteAsync` method keeps its current public contract and persistence behavior: it loads and validates the asset, calls the shared probe core, writes `PingResults`, writes the existing `PingExecute` audit entry, and never changes manual alive status.

Add a dedicated unregistered-address operation accepting `subnetId`, canonical IPv4 text, actor user ID, and cancellation token. Before consuming Ping capacity it must:

1. enforce `PingExecute` permission;
2. load an enabled subnet;
3. require a canonical IPv4 usable address inside that subnet;
4. reject the request if an active server asset currently uses the address.

After probing, it writes only an audit entry and returns `PingProbeResult`. It must not add a `ServerAsset`, add a `PingResult`, or update any asset field.

### Free-Address Page Workflow

Add a separate server-index POST handler and form for free rows. The form posts `subnetId` and `targetIp`; Razor Pages antiforgery remains mandatory. Display controls as `Ping | 登记此 IP` according to independent Ping and create permissions.

Store free-address feedback under a TempData key separate from registered-server feedback. Validate deserialized feedback before using it, redirect back to full-pool mode with the target subnet and exact IP search, force `Skip=0`, and render the feedback only beside the matching subnet/IP row. Free-address feedback never offers `标记为存活`.

Use the existing localized Ping outcome formatting. Return the same safe Chinese responses for permission denial, invalid target, rate limit, and unexpected failures without exposing exception text.

## Audit Design

Use the existing `AuditLogs` schema:

- `Action`: `PingUnregisteredAddress`
- `ObjectType`: `SubnetAddress`
- `ObjectId`: canonical target IP
- `Result`: normalized Ping outcome
- payload: `subnetId`, `targetIp`, `outcome`, `latencyMilliseconds`, and safe `errorCode`

Add Chinese labels for the new action and object type. The payload contains no secrets. Validation failures do not claim a probe result; every completed transport attempt, including timeout, unreachable, and normalized internal error, produces an audit record.

## Data Model, Migration, and Backfill

`PingProbeResult` is not an EF Core entity. `PingResult.ServerAssetId` remains required, and the `PingResults` table remains reserved for registered assets. Existing `AuditLogs` string and JSON payload fields already support the new audit values.

Do not create a migration and do not edit `WebPassDbContextModelSnapshot`. No historical data is backfilled: prior assets, Ping history, and audits remain unchanged, and free-address probe audits begin only after deployment.

The release still follows `DEPLOYMENT.md`, including building and executing the commit-matched migration bundle. With no new migration, the bundle makes no schema or data transition for this feature.

## Testing

- Server-page markup tests verify action order, reveal placement outside more actions, archive-only menu contents, permission combinations, the visible numeric input, `1..500` bounds, and filter `Skip=0`.
- Query integration tests verify invalid low/high values are clamped before service execution, negative offsets are safe, pagination preserves normalized `Take`, and malformed model-binding errors remain visible.
- Ping service tests verify permission, canonical subnet validation, active-registration rejection, timeout propagation, shared mixed-target rate limiting and concurrency, normalized results, audit content, and zero asset/PingResult mutation for free probes.
- Page integration tests verify antiforgery, safe errors, redirect and row-scoped feedback, action permission combinations, no mark-alive action, and no database pollution.
- Existing secret-reveal executable DOM tests and registered-server Ping regression tests remain unchanged and must pass.
- Run focused tests first, then unit and integration projects, followed by the full solution test suite in an environment that supports the offline migration-bundle and SQL Server tests.

## Alternatives Rejected

- A dedicated Razor Page endpoint for free-address Ping would isolate endpoint-level rate limiting but adds routing and duplicates an inventory-specific feedback flow. The service already owns the limit needed by both inventory operations.
- A generic target/persistence-strategy hierarchy would support future probe types but is unnecessary abstraction and exceeds this correction's scope.
- Making `PingResult.ServerAssetId` nullable would mix two histories, require a migration and backfill decisions, and directly violate the requirement not to change the schema.

## Risks

- The existing pool treats an address with only archived asset history as free unless archived rows are included. The new operation follows that active-registration meaning and never changes archived data.
- A registration can occur after the service's active-asset check while ICMP is in flight. The probe still performs no asset or Ping-history mutation; holding a serializable database lock across network I/O would be a worse operational trade-off.
- ASP.NET endpoint rate limiting is attached to the direct registered-server Ping page, while inventory Ping uses the service-level allowance. Applying a limiter attribute to the whole inventory PageModel would also throttle create and archive posts, so both inventory Ping handlers continue sharing the service-level limiter.
- The new audit action and object type must ship with UI labels or existing audit presentation will intentionally fall back to unknown labels.
