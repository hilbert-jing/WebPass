# WebPass v1.2.0 Self-Service Password Change Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a dedicated, audited self-service login-password change page for authenticated, enabled users without changing the database schema or session architecture.

**Architecture:** A scoped `PasswordChangeService` owns user lookup, enablement enforcement, current-password verification, hashing, concurrency handling, and atomic success auditing. An authenticated Razor Page owns form validation, sensitive-value scrubbing, fixed user-facing errors, and PRG navigation; the shared layout exposes the page beside the existing POST logout control.

**Tech Stack:** .NET 10, ASP.NET Core Razor Pages, EF Core 10, SQL Server/InMemory test provider, xUnit, existing Argon2id `IPasswordHasher`, existing `AuditWriter`.

## Global Constraints

- Do not change any EF Core entity, mapping, model snapshot, or migration.
- Do not add a revocation table, session epoch, password timestamp, or duplicate authorization-invalidation mechanism.
- Use only `IPasswordHasher.Verify` and `IPasswordHasher.Hash` for login-password operations.
- Obtain the target user ID only from `ClaimTypes.NameIdentifier`; never accept a posted user ID.
- Require the current `AppUser` to exist and have `IsEnabled == true` on GET and POST.
- The existing password rule is non-empty/non-whitespace only; do not add length, complexity, history, or different-from-current requirements.
- Never place current password, new password, confirmation, old hash, or new hash in audit, status messages, rendered error responses, or exception text.
- Keep current and other login cookies valid; preserve login lockout, Secret Reveal, and reauthentication architecture.
- Use `UserPasswordChange` / `User` / `Success` with no audit payload for a successful self-change.
- Minimize tests: test new security behavior and state transitions, not ASP.NET Core framework mechanics or prose.

```csharp
[Fact]
public async Task Enabled_user_changes_own_password_and_writes_redacted_audit()
{
    await using var db = NewDatabase();
    var hasher = new Argon2PasswordHasher();
    var user = new AppUser
    {
        Username = "operator",
        PasswordHash = hasher.Hash("current-password"),
        MustChangePassword = true,
        FailedLoginCount = 3,
        LockedUntil = DateTimeOffset.UtcNow.AddMinutes(5),
    };
    db.Users.Add(user);
    await db.SaveChangesAsync();
    var service = new PasswordChangeService(db, hasher, new AuditWriter(db));

    var result = await service.ChangeAsync(
        user.Id, "current-password", "new-password", default);

    Assert.Equal(PasswordChangeResultKind.Success, result.Kind);
    Assert.False(hasher.Verify("current-password", user.PasswordHash));
    Assert.True(hasher.Verify("new-password", user.PasswordHash));
    Assert.False(user.MustChangePassword);
    Assert.Equal(3, user.FailedLoginCount);
    Assert.NotNull(user.LockedUntil);
    var audit = Assert.Single(db.AuditLogs);
    Assert.Equal("UserPasswordChange", audit.Action);
    Assert.Equal("User", audit.ObjectType);
    Assert.Equal(user.Id, audit.ActorUserId);
    Assert.Equal(user.Id.ToString(), audit.ObjectId);
    Assert.Equal("Success", audit.Result);
    Assert.Null(audit.Details);
}
```

The rejection theory supplies literal expected outcomes and asserts the original hash remains byte-for-byte equal and `AuditLogs` remains empty.

```csharp
public enum PasswordChangeResultKind
{
    Success,
    UserUnavailable,
    IncorrectCurrentPassword,
    InvalidNewPassword,
    ConcurrencyConflict,
}

public sealed record PasswordChangeResult(PasswordChangeResultKind Kind);
```

`CanChangeAsync` performs an `AsNoTracking` existence query for `Id` plus `IsEnabled`. `ChangeAsync` loads a tracked row, rejects unavailable users and invalid inputs, calls `Verify`, then starts a relational transaction when supported. Set only `PasswordHash` and `MustChangePassword`, save, write this exact payload-free audit, and commit:

```csharp
new AuditEntry(
    user.Id,
    "UserPasswordChange",
    "User",
    user.Id.ToString(),
    "Success",
    null)
```

Catch only `DbUpdateConcurrencyException`, roll back when a relational transaction exists, and return `ConcurrencyConflict`. Let unexpected persistence and audit failures propagate so transaction disposal rolls them back.

Register the service next to `LoginService`:

```csharp

```

- [ ] **Step 3: Implement the Razor Page and sensitive-value scrubbing**

GET parses `ClaimTypes.NameIdentifier` with `Guid.TryParse`, calls `CanChangeAsync`, and returns `Forbid()` unless both succeed.

POST validates the identity and `ModelState`, calls `ChangeAsync`, and maps results as follows:

```csharp
PasswordChangeResultKind.Success => RedirectToPage(),
PasswordChangeResultKind.UserUnavailable => Forbid(),
PasswordChangeResultKind.IncorrectCurrentPassword => PageWithError(
    string.Empty, "当前密码不正确。"),
PasswordChangeResultKind.InvalidNewPassword => PageWithError(
    "Input.NewPassword", "请输入新密码。"),
PasswordChangeResultKind.ConcurrencyConflict => PageWithError(
    string.Empty, "账号信息已发生变化，请刷新后重试。"),
```

Before every invalid `Page()` response, replace `Input` with a new instance. For each password ModelState key, copy its error messages, remove the entry (and therefore its attempted value), and re-add only the messages. On success set `TempData["StatusMessage"] = "登录密码已修改。"` before redirecting.

Render the three password inputs without explicit values, use the autocomplete tokens from the design, include `asp-validation-summary="ModelOnly"`, field validation spans, and a submit button labelled `修改密码`.
